Case study · 2026 · Prototype

Operations workflow agent with approval gates and an audit trail

A 40-request operations queue in which an agent acts on its own only where a written policy says the action is low-risk. Everything above that needs one or two human approvals, three action types can never be run by the agent, and every attempt — executed or refused — lands in a hash-chained log that breaks if anyone edits it.

Built by me · Python standard library, no LLM call, no framework, no database · 21 invariant tests

Measured: 6 of 40 requests run unattended, 29 after approval, 3 blocked by policy, 0 executions below their required approval count, and 9 of 9 bypass attempts refused or detected.

The problem

Automating operations work is easy to demonstrate and hard to trust. The failure that hurts is not an agent that stops when it is unsure — it is an agent that does something irreversible correctly: refunds the wrong batch, re-prices the catalogue, deletes the records, and then leaves a log that says everything was fine.

So the useful question is not "can the agent do the task". It is "what is the smallest set of actions it may take without me, and can I prove afterwards exactly what it did". That sentence is the whole design: policy decides the risk tier, not the agent; a human approves above a threshold; the executor refuses anything the policy has not classified; the log chains each entry to the one before it.

What the agent does, and what stays with a human

The agentThe human
Classifies each request and computes a risk score from the action, the amount and the reachWrites the policy: base risk per action, money and reach limits, the never-execute list
Executes auto-tier actions and records the resultDecides what may be auto in the first place
Prepares the approval step, including the exact payload hash that is being approvedApproves or rejects — and can never approve their own request
Refuses anything below the tier it computes, and logs the refusal with the rule that stopped itRe-runs or escalates a refusal; blocked actions are done by hand in the admin console
Appends one hash-chained audit entry per attemptReviews the chain; an edit anywhere in it breaks every hash after it

There is no language model anywhere in this prototype, and that is deliberate. The gate is the deliverable, and a gate is worth nothing if the thing deciding the risk is the same thing being gated. The proposal step here is a fixed rule table; the parts that had to be right are the tier calculation, the token binding and the log.

How it runs

request (action, amount_myr, blast_radius, requested_by)
        ↓
policy.tier()  ──►  blocked ────────────────► never executed, escalated to a human
        │
        ├─► auto ─────────────────────────► execute → audit
        │
        ├─► single_approval ──► 1 token ──► verify → execute → audit
        │
        └─► dual_approval ────► 2 tokens ─► verify → execute → audit

token  = HMAC(request_id | action | payload_sha | approver | expiry)
verify = signature · request id · payload hash · not expired · approver ≠ requester · distinct approvers
refusal → audit entry carrying the rule that stopped it

The token is bound to the payload, not to the request alone. Changing the amount after approval invalidates the approval, which is the difference between approving "a refund" and approving "a refund of RM500 to this order".

Result: 9 of 9 refused or detected. The last row is the one a reviewer should care about: the chain verified before the edit and broke at the edited entry afterwards, so a doctored log is detectable rather than merely plausible. Testing also changed the code once — an unclassified action type was falling through to dual approval instead of being refused, which the test for "an unknown action is never auto" caught. The policy now fails closed: if it cannot classify an action, nobody can approve it either.

Two requests, side by side

RQ-001 — schedule a social post, reach 40: base risk 4, no money, reach under the limit → auto. It runs, and the log records the action, the tier, an empty approver list and a payload hash.

RQ-036 — change the payout bank account: on the never-execute list → blocked at any risk score, with any number of valid approvals. The agent does not get to touch where money is paid out; a human does that inside the admin console, and the agent's log shows the request was escalated rather than performed.

RQ-016 — refund a batch of orders after a pricing error, RM4,200, reach 9,000: base 28 plus money and reach → score 68 → dual_approval, and marked irreversible, so two different people must sign two different tokens naming that exact amount.

Limitations — what this does not show

  • The approvals are simulated. A scripted stand-in approver approves up to RM5,000, rejects above it, and leaves one request unanswered. The gate is real code; the humans are not, and this says nothing about how real approvers behave under load or under pressure.
  • Side effects are simulated. The executor records what it would have done instead of calling a store API, so the claim is about the gate and the record, not about integration with a real system.
  • No LLM. Nothing here demonstrates model orchestration, prompt design or agent planning. It demonstrates a permission boundary and an audit trail around an automated workflow.
  • One policy, one queue, 40 requests. The tier table is my judgement, not a calibrated model; a different incident history would move the thresholds.
  • The hash chain is tamper-evident, not tamper-proof. An attacker who can rewrite the whole file from entry 1 can rebuild the chain; detecting that needs an external anchor (a signed daily digest), which this prototype does not have.
  • Single-user local demo. No authentication, no multi-tenant separation, no rate limiting, no retention policy.
